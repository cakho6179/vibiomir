## 1. Code đã có

| Đường dẫn | Vai trò |
|---|---|
| `r2ai2026/scoring.py` | Bản sao cục bộ luật chấm: normalize (NFKC → HTML entities → lowercase → collapse ws), token LCS, ngưỡng `>= 0.40`, macro F2 hai cấp, helper tune độ sâu nộp |
| `r2ai2026/text.py` | Chuẩn hóa + tokenize (bỏ dấu tiếng Việt, char+bigram cho tiếng Trung), `detect_lang`, `sentence_spans` |
| `r2ai2026/corpus.py` | Đọc `links_corpus_vi_en_zh.parquet`, phân loại `pubmed/vi/zh/other`, thống kê host, sampling theo host |
| `r2ai2026/fetch.py` | Crawler async (httpx): robots.txt, giới hạn đồng thời toàn cục + theo host, retry/backoff, trích xuất trafilatura (fallback lxml) |
| `r2ai2026/pubmed.py` | Harvest PubMed qua E-utilities (efetch XML → title + abstract), rate-limit 3 req/s (10 req/s nếu có API key) |
| `r2ai2026/chunking.py` | Chunk theo câu (target/overlap), `merge_selected` (giữ thứ tự tài liệu), `whole_document_chunk` (cắt tại ranh giới câu) |
| `r2ai2026/bm25.py` | BM25 (bm25s) cho cấp doc và cấp chunk, lưu/load kèm `rows.npy` + `params.json` |
| `r2ai2026/pipeline.py` | Pipeline end-to-end: corpus → index → retrieve → chọn chunk → submission |
| `r2ai2026/submit.py` | Đóng gói ZIP (đúng 1 file `submission.json`) + validator (id trùng, kiểu dữ liệu, chunk rỗng, kích thước) |
| `r2ai2026/devproxy.py` | 2 proxy không cần nhãn: title-as-query (recall@k, MRR) và pseudo-gold span (đo đúng luật chunk) |
| `r2ai2026/store.py` | JSONL append-only + SQLite resume cho crawl |

CLI:

```powershell
python scripts\r2ai2026_fetch.py pubmed --limit 800          # harvest PubMed
python scripts\r2ai2026_fetch.py web --limit 5000 --kinds vi,zh --per-host-cap 20 --resume
python scripts\r2ai2026_build_index.py --docs data\r2ai2026-vibiomir\docs.jsonl --index-dir runs\r2ai2026\index --chunk-source bm25_merge
python scripts\r2ai2026_run.py --docs ... --queries data\r2ai2026-vibiomir\query.parquet --index-dir runs\r2ai2026\index --submission runs\r2ai2026\submission.zip --chunk-source doc_head --topk-docs 20
python scripts\r2ai2026_devproxy.py --docs ... --index-dir runs\r2ai2026\index
python scripts\r2ai2026_benchmark_scoring.py                 # đo thời gian chấm của scorer replica
```

Tests: `python -m pytest tests -q` → **95 passed**.

## 2. Đo lường thật (2026-10-18/19)

| Chỉ số | Giá trị |

### 2.4 Chi phí chấm (scorer replica, `rapidfuzz`)

| Kịch bản | Số chunk | Thời gian |
|---|---|---|
| 1.200 query × 5 doc × 3 chunk @400 token | 18.000 | 6,8 s |

→ "Nộp cả bài" tốn ~14× thời gian chấm; vẫn dưới hạn 600 s nhưng phải chừa biên (máy BTC là `codalab-legacy:py37`).

### 2.5 Dev-proxy (400 doc)

Title-as-query: `recall@1 = 0.986`, `MRR = 0.991` (corpus nhỏ nên dễ; sẽ giảm mạnh khi corpus lớn lên — dùng để so sánh tương đối).

Đường cong ngân sách chunk (luật chính thức vs pseudo-gold span):

| Budget (token) | Chunk P | Chunk R | Chunk F2 |
|---:|---:|---:|---:|
| 200 | 0.910 | 0.818 | 0.828 |
| 400 | 0.965 | 0.926 | 0.931 |
| 800 | 0.995 | 0.980 | 0.982 |
| **1400** | **1.000** | **0.999** | **0.999** |
| 3000 | 1.000 | 1.000 | 1.000 |

→ Xác nhận giả thuyết trung tâm: **một chunk dài (một chunk/tài liệu) là chiến lược đúng** dưới luật `LCS/|gold| >= 0.40`; nút thắt chuyển từ "chọn chunk" sang "kích thước payload" và "thời gian chấm".

## 3. Suy luận về baseline của BTC

`DOCS_P=0.8805`, `DOCS_R=0.5146` → `n_submitted / n_gold = R/P = 0.584` (nộp **ít hơn** số gold doc). Vì F2 nghiêng recall, BTC đang bỏ điểm ở cấp doc: chỉ cần tăng recall mà giữ precision ~0.8 thì DOCS_F2 có thể lên ~0.8 (từ 0.5587).

`CHUNKS_P=0.3403`, `CHUNKS_R=0.1755` → chunk của BTC ngắn/không khớp ngưỡng. Với chunk dài (≥800 token), proxy cho thấy CHUNKS_F2 ≥ 0.9 *nếu* tài liệu gold được retrieve đúng.

⇒ Điểm nghẽn thật của cả hai cấp là **corpus coverage + recall ở cấp doc**, không phải chất lượng xếp hạng chunk.

## 5. Việc tiếp theo (đề xuất)

1. **Crawl lớn**: VI/ZH theo thứ tự host nhiều URL nhất + harvest toàn bộ 240k PubMed (rẻ, chắc chắn).
2. **Bổ sung dense retrieval** (BGE-M3 hoặc Qwen3-Embedding) trên Kaggle T4 cho phần còn thiếu của recall, kết hợp RRF với BM25.
3. **Tối ưu chọn top-k theo F2** bằng các helper `depth_curve_*` trong `scoring.py` (dùng proxy).
4. **Kiểm tra giới hạn dung lượng submission** trước khi chốt chunk budget.
5. **Quyết định chiến lược chunk cuối** sau khi biết kích thước payload cho phép.

### 6.4 API Wayback — hành vi thật (đo 2026-10-19)

| Truy vấn | Kết quả thật |
|---|---|
| `matchType=domain&collapse=urlkey` | **503** (Internet Archive Temporarily Offline) |
| `matchType=domain` (không collapse), limit 3000 | 200 sau 41,5 s, nhưng 3.000 dòng đầu toàn `.json` + homepage → **0/79.598 URL của corpus**, và còn phải phân trang rất nhiều |
| `matchType=prefix` trên namespace bài viết | 504 Gateway Timeout (Long Châu) / 503 (familydoctor) / 162 unique trong 500 dòng (120ask) |
| `matchType=exact` cho 1 URL | **200 trong 0,3–1,6 s**, chính xác → đây là API dùng được |
| `/web/2020/<url>` (tải snapshot) | 200, trích xuất OK |
| `archive.org/wayback/available` | 429 (rate limit) |

⇒ Chiến lược wayback: tra **exact theo từng URL**, tốc độ thấp + backoff (không dùng domain/prefix/collapse). 79.598 URL Long Châu × ~0,5 s (tra) + ~1–3 s (tải snapshot) → cần chạy nền nhiều giờ, ưu tiên host lớn nhất trước.

### 6.5 Bài học phương pháp

1. Mock không chỉ vô ích mà **che giấu lỗi nghiêm trọng**: bug charset (217k URL) và bug CJK là hệ quả của giả định Latin-only.
2. Test bằng HTTP server thật (socket thật) phát hiện ngay bug `netloc`, lỗi decode, lỗi robots — chi phí gần bằng mock, giá trị cao hơn hẳn.
3. Số liệu "cảm tính" phải được thay bằng đo: tỉ lệ OK thật chỉ 83 %, không phải 95 % như kỳ vọng.
4. Với 1,22 M URL, **lỗi ở tầng host quan trọng hơn lỗi ở tầng URL**: circuit breaker tiết kiệm hàng trăm nghìn request.
